# ADR-0008：未跟踪条目删除的边界

- 状态：Accepted（2026-10-18，迁移自现有实现）
- 相关：`src/host/actions.ts`、`src/host/queries.ts`、issue #46
- 后续：ADR-0024 加了第二项写盘动作（编辑白名单内的已有文件）

## Context

「放弃未跟踪条目的更改」是插件里**唯一直接删盘**的操作：未跟踪文件不在 index 里，`git restore` 摸不到它们，要放弃只能由 host 自己删。

这带来两个必须回答的问题：

1. 删什么？未跟踪条目可能是文件、普通目录、嵌套 Git 仓库、子模块，或 bare 布局。删掉一个「目录」如果它其实是别人的仓库，损失远超用户预期。
2. 失败怎么办？批量删除时某一条失败（权限、竞态、条目在删除过程中变了），静默跳过会让用户以为已经清理干净。

历史上这条边界反复调整过：早期版本会连带删除嵌套仓库，issue #46 之后改成整批拒绝；同时明确「只**包含**仓库的普通目录仍然整体删除」——这条看起来不一致的规则是刻意的。

## Decision

- 删除前逐条判定：条目**本身**是仓库（嵌套仓库 / 子模块 / bare 布局）时**整批拒绝**，返回 `nested-repo`，不做部分删除。
- 只「包含」仓库的普通目录仍整体删除——目录本身不是仓库，用户放弃的是自己的工作区内容。
- 删除循环内**逐条复检**：判定与删除之间条目可能变化（竞态），命中时报 `nested-repo-partial`，明确告知「它之前的条目已被删除」，绝不静默。
- 任何删除失败都汇总成错误返回，不做「尽力而为、失败就跳过」。
- 入口同时受 ADR-0006 的路径校验与 realpath 包含检查约束：软链指向仓库外一律拒绝，`.git` 不可浏览。
- 这两条边界（整批拒绝 / 包含仓库的目录仍删）由单测同时锁住，改一条必须同时改测试与 ADR。

## Consequences

- 用户不会因为一次批量放弃而丢掉一个嵌套仓库；代价是「一批里有一个子模块」会导致整批失败，需要用户手工处理那一条。
- 部分失败会留下「删了一半」的状态，但它是**显式报告**的，不是静默的——用户知道要刷新确认剩余变更。
- 删盘是不可逆的，所以这条路径永远伴随二次确认（ADR-0007），且「放弃」只作用于工作区侧。
