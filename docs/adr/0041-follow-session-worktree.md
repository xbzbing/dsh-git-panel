# ADR-0041：跟随会话的实时工作目录，只在同一仓库的检出之间切换

- 状态：Accepted（2026-11-26）
- 相关：PR #100（已回退）、ADR-0035、ADR-0038、`src/client/follow-checkout.ts`、`src/client/checkout-controller.ts`、`src/client/use-session-checkouts.ts`、`src/client/registry.ts`、`src/client/GitPill.tsx`、`src/client/Panel.tsx`、`src/client/repo-select.ts`、`src/host/core.ts`、`src/host/index.ts`

## Context

平台会把会话的实时工作目录投影成 `workingDirectory`，`enter_worktree` / `exit_worktree` 会原地改写它；而会话的 `header.cwd` 是创建时的元数据，永远不变。Git 面板此前只认 `header.cwd`：用户进入本仓库的 worktree 后，面板仍停在主检出，必须去仓库列表手动点一次。

PR #100 曾经让面板跟随 `working_directory`，随后被回退。回退的理由不是「不该跟随」，而是那次跟随没有边界：它把「会话搬到了另一个目录」直接等同于「Git 上下文换一个根」，会把面板带进无关的嵌套仓库或 `.code-workspace` 认证的外部根，等于悄悄推翻了 ADR-0030 / ADR-0035 的「一个请求一个根、外部根只在选中后生效」。另外，自动选择如果写进标签页的 pick 记录，会变成用户从未做过的意图（ADR-0038）。

这次只解决一个具体场景：会话在本仓库自己的检出之间移动（主工作树 ↔ `.agents/worktrees/<branch>` 等 `git worktree` 检出），输入框标记与面板跟着走，其它目录变化一律不跟。跟随不能绑定在面板挂载上：只看输入框标记时也要生效，而对话页与侧栏同时挂载时不能重复扫描或各自判断手动选择，因此列表与跟随属于会话共享生命周期。

## Decision

1. **客户端跟随，host 不改 RPC 行为**。输入框标记与面板从各自槽位拿到平台的 `useProjection`，读 `workingDirectory`，交给每会话一个共享检出生命周期处理；标记单独挂载时也能跟随，不依赖面板打开。宿主不提供这个 prop 时按「不跟随」处理，保持原来的手动切换。新增的 host 侧只有配置：`followSessionCheckout` 默认 `true`、`.volatile()`，随现有快照下发；旧 host 的快照没有该字段时客户端按关闭处理，没有 ready 样本则是「未知」，不是关闭。
2. **只跟随本仓库的检出**。目录先按「最长根」归属到唯一一行，再由这一行决定能不能跟：工作区行（`path: ''`）直接可信（它的根就是会话自己的检出，会话本身在 linked worktree 里时也由它承载），其余行必须是 `role: 'main' | 'linked'`。`disabled`（cwd 外未认证、stale）和 `role: 'repo'`（扫描到的嵌套仓库、`.code-workspace` 外部根）一律返回「不跟」，且**不回退到祖先行**——宁可不动，也不把面板带到一个不是会话当前所在的检出。
3. **进入和退出都跟；手动选择优先**。自动切换走 `followRepo`：只改内存里的选择，不写 `sessionStorage`、不记 `rootPick`，因为它不是用户的意图；`hasRepoPick` 也把自动选择当作没有选择，修复自动行时不会覆盖用户此前存下的手动记录。用户手动点过一行后，面板保持这一行：刷新 / 热重载重新挂载时、同一目录的重取 / 探测失败窗口内、以及之后的每次判定，都不会因为目录仍停在 worktree 就把它改回自动结果（这是 ADR-0038 的承诺）；只有 `workingDirectory` 真的变化，或开关从关闭切到开启，才重新跟随。开关切到开启时对当前目录立即跟随一次，不等下一次目录变化。手动选择被 host 判定为已消失时不受保护：修复清掉选择后，共享生命周期的下一次判定就按当前目录重新跟随——被保护的选择记在跟随状态的 `manual` 里，目录一直留在 `pending` 作为否决后的回退目标，不依赖「挂载后的第一次判定」。判定收在 `follow-checkout.ts` 的 `planFollow`：输入目录、列表、当前选择、开关与跟随状态，输出「不动 / 重取一次 / 跟随某行」，共享检出生命周期保存唯一跟随状态并执行副作用；组件不各自运行判定，新增面板也不重新解释已有手动选择。
4. **列表里还没有这一行时，只重取一次；探测失败时保留待判目录**。新建的 worktree 是主检出下的一个新目录，上一次扫描不可能知道它；如果直接按包含关系跟随，只会得到主检出（错误）。所以「目录落在某个可信行之下、但不是任何行的根」时由共享生命周期触发一次 `repo-list`，等本次应答后再判定；多个标记 / 面板合用这一请求，在途时旧列表可以继续展示，但不能据此提前跟随父行。新行出现就跟过去；仍然没有，则按最具体的覆盖行跟随（会话创建工作区子目录的常见情况）。worktree 探测失败时按「列表不完整」处理：不跟随父行，也不修剪手动记录——手动选择继续生效，目录保持 `pending` 作为回退目标，等下一次 `repo-list` 应答（重新挂载、切回可见或其他读取）再判定；这里不额外安排一次重取。
5. **路径比较按宿主机形状归一化**：反斜杠转正斜杠、去尾部隔符；Windows 盘符 / UNC 路径大小写不敏感，POSIX 区分大小写。不做 realpath 解析——客户端拿不到 realpath，词法路径与 host 的 realpath 不一致时降级为不跟随，而不是猜一个根。
6. **跟随不改变当前页签**，切换沿用既有的「旧样本保留 + 变暗 + switching 标记」；已缓存的样本直接切换，不闪。同一会话的所有面板都按共享选择与样本归属判断在途状态，旧样本对应的内容必须 inert，不能只有触发切换的面板禁写。
7. **自动跟随不弹未保存编辑的确认**。手动切换仓库会先问文件浏览器里的未保存编辑（`chooseRepoGuarded`）；跟随由平台移动会话触发，没有可等待的点击，共享生命周期直接更新选择并切换现有快照控制器。草稿本身不丢：它记着自己开始编辑时的根（`rootKey` / `rootPath`），在新根下显示为「草稿属于另一个检出」的提示，仍可保存或放弃；需要继续看着草稿的用户可以关掉跟随，或用仓库选择器切回原检出。
8. **列表与跟随按会话共享，不复制快照**。`registry.ts` 为每会话维护一个检出生命周期，与现有 `GitController` 配对；输入框标记、对话面板和侧栏面板只提交投影 / 可见性输入并订阅同一份列表。列表请求单飞，仓库选择和普通快照轮询不触发重扫；配置变更、连接重置、面板切回可见和跟随所需的重取统一失效。请求按会话和失效代次归属，迟到应答不得覆盖新状态；配置只接受较新的 ready 样本，旧会话或检出缓存不能把开关翻回去。修复后再跟随，判定读当前选择，样本否决只修复该样本所属的选择。各挂载独立释放引用，卸载一个实例不影响其余实例；空闲回收与插件卸载清理请求和订阅。

## Consequences

- 平台 `enter_worktree` / `exit_worktree` 之后无需手动点仓库列表，也无需先打开 Git 面板：输入框标记单独挂载即可驱动共享选择。`.agents/worktrees` 池、外部创建但经认证的 worktree 都覆盖。外部根、无关嵌套仓库和任意的 `working_directory` 改动仍然需要手动选择，ADR-0030 / ADR-0035 的边界不变。
- 同一会话的多个标记 / 面板共用列表、跟随状态和现有快照控制器；新增挂载不增加独立扫描或快照，关闭一个面板也不停止仍有订阅者的跟随。
- 自动选择不写标签页记录：刷新、热重载不会把自动结果当成用户偏好；用户手动选择后照常持久化，且优先于挂载时的自动跟随。
- 目录不是任何行的根（例如会话创建工作区子目录、或列表缺行）时会多发一次 `repo-list`；这是为「新 worktree 不在旧列表里」付出的固定代价，每次目录变化最多一次。列表探测失败时不跟随父行、不修剪记录，目录保持 pending；后续判定由下一次 `repo-list` 应答（切回可见或重新挂载）触发，不额外安排重取。
- 手动选择被确定否决时记录会删掉；`unverified` 的否决、git 暂时没应答只清内存，记录保留到下一次加载。删除发生在会话中途也不会终止跟随：共享生命周期会按当前目录重新跟随，面板不会停在默认检出。
- 自动跟随可能让正在编辑的文件草稿脱离当前浏览器根；草稿会保留并标注它属于哪个检出，不会静默丢失，但自动切换本身不再询问。
- 词法路径与 realpath 不一致（符号链接工作区）时跟随会静默失效；这是已知降级，平台若改为下发规范化路径应重新评估匹配。
- 旧 host 缺少投影 prop 或快照字段时完全退回手动切换，不报错、不写配置。
- 与 PR #100 的区别：这次只跟随「本仓库自己的检出」，且只由投影驱动；不把 `working_directory` 当作 Git 根的通用来源，也不改变「一个请求一个根」。
